# 單元測試與回歸測試

---

## 單元測試 ( Unit Test )

### 創建單元測試的主要步驟
- 設置數據(假想的數據)
- 使用被測試類型的功能
- 比較實際結果和預期的結果。

### 單元測試的11大原則

- 技術模塊的規格說明書要寫詳細，各項要求可表示為一個測試用例。
- 將這一單元要做的事和此單元不能做的事，用單元測試清晰的表達出來。同時單元測試亦能幫助紀錄這個模塊的歷史和設計變更的理由。
- 單元測試應該測試程序中最基本的單元，例如C++/C#/Java中的類；例如python、javascript中的函數 (Functions)、類別的方法 (Class Methods)、類別 (Classes)、模組中的函數 (Module Functions)。在此基礎上，可以測試一些系統中最基本的功能點(這些功能點由幾個基本類組成)。
- 單元測試要測試API中的每一個方法及每一個參數。
- 單元測試必須由最熟悉代碼的人撰寫
- 單元測試後，機器狀態不變，單元測試後，不要改動到原有的目錄結構、代碼內容、數據庫內容等。
- 單元測試要快。因為一個軟件中有幾十個基本模塊(類)，每個模塊又有幾個方法，所以基本上要求一個類的測試要在幾秒內完成。
- 單元測試應該產生可重複、一致的結果，確保增加測試的真實性。
- 單元測試需要有獨立性，單元測試的運行、通過、失敗，不依賴於別的測試。並且單元測試時，可以人為構造數據，以保持單元測試的獨立性。
- 單元測試應該要覆蓋所測單元的所有代碼路徑，包括錯誤處理路徑。以及為了保證代碼覆蓋率，單元測試必須測試公開的私有函數和方法。需要確保這個模塊的每個函數、每個語句、每個條件分支、每個布林值(TRUE/FLASE)都覆蓋了嗎?
- 單元測試應該集成到自動測試的框架中，將單元測試自動化後，可以使每個人能隨時、隨地運行單元測試。並且在每日構建之後，運行單元測試，確保單元測試的錯誤可以即時被發現並得到修改。
- 單元測試代碼必須和產品代碼一起保存和維護，以確保單元測試和實際產品代碼保持一致，以免後續單元測試跟不上實際的代碼內容。

## 回歸測試 (Regression Test)

也就是繼單元測試之後的測試。當我們全部的單元測試都通過之後，以此為一個此模塊的功能基準線，但之後在新個構建中出現了問題，這個模塊就出現了一個退步(Regression)。例如，在3.1.5 版本中，模塊A的編號為125的測試用例通過了，但是到了3.1.6版本，這個125號的測試用例失敗了，這便是一個倒退(Regression)。而工程師應該在新版本上運行所有已經通過的測試用例，以驗證沒有退化的情況發生，這個過程就是一個 Regression Test 。

所以，針對一個 Bug fix ，我們需要做 Regression Test 目的有二。其一，驗證新的代碼的確修正了缺陷。第二，驗證新的代碼有沒有破壞模塊的現有功能，有沒有regression退化。
