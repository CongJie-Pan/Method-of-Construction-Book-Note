# 構建驗證測試(BVT)介紹及相關流程說明

---

目前要介紹的是構建驗證測試，英文叫做 Build Verification Test，簡稱 BVT，也有時被稱為 Build Acceptance Test（BAT）。

構建驗證測試，顧名思義，就是在一個構建完成後，構建系統會自動運行一套測試，用來驗證系統的基本功能。在大多數情況下，這些驗證步驟會在自動構建成功後自動運行，但有時也會手動觸發。

由于這些構建通常是自動生成的，我們也要盡量讓 BVT 能自動運行。在運行 BVT 之前，我們可以先運行所有的單元測試，以確保系統的單元測試和開發人員本地的單元測試版本是一致的。因為在不少情況下，開發人員會修改程序和單元測試，但忘記將修改後的單元測試一同提交到代碼庫中。

通過 BVT 的構建，我們可以認為該版本是可測試的，也就是說，團隊可以基于這個版本進行各種測試，因為它的基本功能已經可用。反之，如果沒有通過 BVT 的構建，就被稱為失敗的構建。

如果構建驗證測試沒有通過，自動測試框架會針對每一個失敗的測試自動生成一個問題，也就是自動生成一個 bug。

一般來說，這些 bug 都會被賦予最高優先級，也就是說，開發人員需要優先處理這些問題。大家都知道，維持每天的構建能夠産出一個可測試的版本，這是軟件開發過程中質量控制的基礎。

那麽，對于導致構建失敗的 bug，我們應該如何處理呢？首先，要找到導致失敗的原因。如果原因比較簡單，程序員可以立即修複並直接提交代碼。其次，需要定位導致失敗的修改集，然後將這個修改集從當前版本中剔除。也就是說，程序員必須先修正 bug，再將修正後的代碼重新提交到源代碼庫中。這樣，程序員必須在下一個構建開始之前完成 bug 的修複。

方法一和方法二都可以保證當天的構建是可測試的，但有些問題可能相互依賴，無法在短時間內全部解決，這時就需要采用第三種方法。

這裏就涉及到另一種測試方式——冒煙測試。冒煙測試其實是借鑒了硬件設計行業的做法，主要用于基本功能的驗證。也就是說，先用最基本的功能測試，看看系統能否通過，確保核心功能可用。

以上就是關于構建驗證測試的全部內容。
