# 軟件驗收測試流程與質量評估方法

---

接下來我們講講驗收測試，也就是 acceptance test。首先，驗收測試指的是測試團隊在拿到一個可測試的構建後，會按照測試計劃，對各自負責的模塊和功能進行測試。在這個過程中，可能會發現十幾個，甚至上百個 bug。

那麽，如何才能有效地測試軟件？在這個階段，又該如何衡量構件的質量呢？在 MSF 的敏捷模式中，建議采用場景來規劃測試工作。具體來說，首先要在基本場景的基礎上，把系統理論上目前支持的所有場景都列出來，然後按照功能分類進行測試。

如果測試通過，就在該場景中標記為“成功”；如果失敗，則標記為“失敗”，並用一個或多個 bug 來描述失敗的情況。當所有測試人員都完成了場景測試後，我們可以通過下面這個表格來了解場景測試報告的整體情況。

這個場景測試報告有四個字段：第一個是場景 ID，第二個是場景名稱，第三個是場景結果，第四個是 bug ID。例如，場景 ID 是 3024，場景名稱是“用戶登錄”，測試結果為“成功”，因為測試通過，所以 bug ID 那一欄就是空的。

接下來我們再舉一個例子，比如場景 ID 為 3026，它的場景名稱是“用戶按價格排序”。該場景的測試結果是失敗的，因此對應的 bug ID 是 5032。

再舉最後一個例子，場景 ID 為 3027，場景名稱是“用戶按名字搜索”，測試結果同樣是失敗的，對應的 bug ID 是 5033。

通過這樣的測試報告，我們可以清楚地了解各項功能的測試通過率。例如，如果所有場景都能通過測試，說明功能覆蓋率達到了 100%。在某些情況下，標準也可以適當放寬，比如將通過率標準從 100% 降至 90%左右。只要達到這個標準，就說明該構件的質量已經可以滿足使用需求，可以作為一個版本交付給用戶。在這種情況下，客戶和合作夥伴就能獲得這個版本，這也就是所謂的“技術預覽版”或“社區預覽版”的由來。

不過，這裏需要特別注意一個重要問題：可用並不意味著軟件的所有功能都沒有問題，而是指在當前用戶場景下，按照場景要求進行操作時，能夠達到預期效果。因此，這種測試被稱為“驗收測試”。如果構建通過了這樣的測試，就會被測試團隊接受。同時，還可以針對系統的不同方面進行驗收測試，比如系統的全球化驗收測試，或者針對某一特定語言、環境或平台的驗收測試。
